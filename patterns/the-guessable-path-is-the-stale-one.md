# The Path You Can Guess Is the Stale One

An app kept its state in two tiers:

```
~/.cache/lm-studio/.internal/…              app-level
~/.cache/lm-studio/apps/<app>/.internal/…   per-app   <- what the client actually reads
```

A client that ships its own backend uses the **per-app** tier. The app-level copy still exists, still has a plausible mtime, and is never read. Patching a chat template there produced no error and no change — the identical failure, with a correct fix on disk.

The generalization is not about this app. Wherever a tool grew profiles, workspaces, or embedded clients, the **top-level path is the one you can guess and the one that is wrong**: VS Code profiles, browser profiles, `XDG_*` overrides, Docker named volumes vs bind mounts, per-workspace vs global settings, a repo `.git/hooks` shadowed by `core.hooksPath`. The guessable path is the original, single-tenant one; the live path is the one added when the tool learned to host more than one thing.

## Why it survives being found once

Both halves matter, and the second is the expensive one.

The tier rule above was discovered while chasing the template bug, applied there, and **then not reused twenty minutes later** when the question became "where is today's log?" — the app-level `server-logs/` was searched, found empty, and reported as "no log written today" while the client was actively writing one in `apps/<app>/server-logs/`.

Nothing was forgotten. The finding simply stayed attached to the problem that produced it instead of becoming a thing you *search with*. That is the normal fate of a structural discovery made mid-debug: it reads as a fact about this bug, not as a fact about this filesystem.

## The Pattern

**1. When a path lookup fails or a fix does nothing, enumerate before you re-guess.** Absence at the guessable path is not evidence of absence; it is evidence you looked at the tier nobody writes to. The second guess is almost always another guess.

**2. Promote the layout into a tool, not a note.** A rule written in prose gets applied to the next instance only if the reader recognises the instance — and the whole failure above is a *non-recognition*. A twenty-line script that enumerates every root and prints which is live cannot fail to be recognised, because you run it by name:

```
logs      LIVE  apps/bionic/server-logs/2026-08/2026-08-04.1.log   6.1KB  2m ago
                (21 older/shadowed in: app-level — --debug to list)
```

Rank by mtime and say *which one is live*, rather than printing candidates and leaving the judgement to the reader who already guessed wrong once.

**3. Show the shadowed copies, don't hide them.** The stale file is the thing that will be edited by mistake, so it belongs in the output — behind a `--debug` flag so the default stays a single legible line per concern. Concise-by-default with an opt-in verbose mode is what keeps such a tool in use; a wall of paths gets skimmed.

**4. Read configurable roots from config, never assume them.** The same app let the model directory be relocated (`settings.downloadsFolder`). A map that hardcodes a root it could have read is the same bug one level up.

**5. Its selftest asserts the miss.** Not "does it list files" — construct an old app-level twin and a recent per-app file and assert the per-app one wins *and* the shadowed one is still reported. A map that happens to be right on today's machine is not a map.

## Finding the right file is not the end of it

Two follow-ons, both found while *verifying* a fix that had already landed in the correct copy.

**A banner is not a version.** The patched template still opened with `Template: Google Gemma 4 Canonical Chat Template / Published: 2026-07-09 / Context: Fixed tool-calling loops…` — sitting inside a file hand-edited hours earlier, because a header is text and text survives an edit. Any provenance a file asserts about itself (`canonical`, `fixed`, `generated by`, `DO NOT EDIT`, a version stamp) describes the moment it was written, not the bytes below it now. Grep for the construct you care about; never read the banner as a state check. This is how a correctly-patched file later convinces you it is pristine, and how a stale one convinces you it is current.

**A shared store patches per entry, not per class.** The per-app index held *every* installed model's template in one file. A whole-file find-and-replace fixed the entries present at the time and left siblings re-indexed afterwards untouched — three of them still carrying the exact bug, latent until something exercised that code path. When a single file is a container for many independent records, "I fixed the file" and "I fixed the thing" are different claims. Verify per record, keyed on each record's own field.

**And the persistent config you want to write may be user-write-only.** The store existed and was *empty*: the app writes it the first time a human changes a setting in its UI, so there was no schema to write against and no file to edit. An agent should say that rather than invent a format — then, once the user changes one value, the real shape is readable and the rest can be set safely. The key vocabulary usually ships in the app bundle (`grep -rho "llm\.load\.[a-zA-Z]*"`), which turns the remaining fields from guesses into lookups.

## The tell

You type a path from memory, get an empty result, and your next move is a different path from memory. That second guess is the moment to stop and enumerate — it costs one command and it is the only cheap point in the whole sequence.
