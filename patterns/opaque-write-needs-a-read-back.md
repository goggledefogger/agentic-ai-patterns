# A Write's Success Confirms the Write, Not the Content

Storing an OAuth credential, the operator pasted a command containing the documentation's placeholder ellipsis characters instead of the real values. The secret manager returned a full success block: item ID, vault name, version, all three fields listed. Each field showed as concealed, "use --reveal to reveal," which is correct behavior for a credential and also meant the garbage was invisible. Nothing in the success output could distinguish a stored secret from a stored "…". It was only caught by reading the field back.

## The Pattern

For any write whose payload is opaque by design, secrets, encrypted blobs, binary data, a write-only API, the success receipt confirms the WRITE happened and says nothing about the CONTENT. The check is a read-back, never the receipt.

This bites harder than the ordinary "trust but verify" reminder because the usual human backstop, glancing at the value as you type it, is exactly what concealment removes on purpose. A visible field lets a typo catch your eye on the way past. A field that's masked by design (correctly, for a credential) closes that path, so the read-back isn't a nice-to-have, it's the only check left.

Verify the content, not the transaction:

- Read the value back through the same interface a real consumer would use, and compare it (or its hash) against what you meant to send, not against what you sent.
- A masked field in the success output is not evidence. "Concealed" and "correctly stored" produce the identical response.
- Placeholder text in documentation (`...`, `<your-value-here>`, ellipsis characters) is the specific trap: it's syntactically valid input, so nothing upstream of the write rejects it.

## Related Failure, Same Session

A shell fix wrapped in `|| true` that silently no-opped looked identical to a working fix in every log. Same family: a success signal that structurally cannot fail carries zero information about whether the underlying thing happened correctly. `|| true` swallows the exit code the same way a masked field swallows the payload, both convert "did this work?" into a question the receipt was never built to answer.

## Why It Works

- A receipt is generated by the write path succeeding, not by the payload being correct. The two are independent facts, and only one of them is what you actually care about.
- Read-back forces the check through the same serialization/storage round-trip a real reader would hit, so it also catches encoding or truncation bugs the write path itself can't see.

## When to Use

- Any write to a secret store, encrypted field, or write-only API, where the interface won't show you what landed.
- Migrating or bulk-loading credentials, especially from a documented example that contains placeholder values.
- Reviewing a shell script for a command whose failure is suppressed (`|| true`, `2>/dev/null`, an unchecked exit code) — ask what content-level check exists if the command silently no-ops.
