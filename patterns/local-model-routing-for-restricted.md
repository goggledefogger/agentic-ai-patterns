# Local-Model Routing for Restricted-Tier Content

A forward-looking pattern: when a vault file carries `sensitivity: restricted`, route any LLM-driven processing (summarization, drafting, Q&A, transcript extraction) to a **local model** that never crosses the network boundary. The cloud model handles everything else. The `sensitivity` frontmatter property becomes the routing key.

**Status as of 2026-05-05:** not yet implemented. Capable local models exist for many tasks, but the routing layer, the policy enforcement, and the workflow wiring are still to-build. This pattern documents the target shape and the path to get there.

## The Problem

[`sensitivity-tiered-access-control.md`](sensitivity-tiered-access-control.md) covers the present-tense layered defense: tagging, hook gating, conventions. Its current ceiling is the `restricted` tier's "ask first" policy — any restricted read requires a per-task user authorization. Once authorized, the content flows to whatever model the agent is using, which today means a cloud model (Claude on the Anthropic API, GPT on OpenAI, Gemini on Google).

That ceiling is fine for occasional use. It's not fine as a long-term posture for content that should structurally never leave the local machine — counseling notes, draft separation conversations, health context, certain legal materials, internal investigation notes.

The user's options today:
1. **Don't process restricted content with AI at all.** Loses leverage where it matters most (these are often the situations where careful drafting and synthesis are highest-value).
2. **Authorize per-task and live with cloud processing.** Works in practice. Carries an irreducible privacy cost.
3. **Run a local model for restricted content only.** What we want. Today: not yet practical for most workflows.

## The Pattern (target shape)

Three components. None individually exotic. The pattern is the wiring.

### 1. The routing key is the existing `sensitivity` property

No new schema. The agent or pre-tool hook reads `sensitivity:` from frontmatter and routes accordingly:

| Tier | Routes to |
|---|---|
| `public` | Cloud model (the default) |
| `internal` | Cloud model |
| `confidential` | Cloud model (in private session, no logging beyond the agent's normal behavior) |
| `restricted` | **Local model only.** Network egress for the content of this file is a policy violation. |

Reusing the existing property keeps the schema honest. If a workflow for a `confidential` file later turns out to need local-only too, that's a tier downgrade decision, not a new property.

### 2. The local model is selected by capability tier

Local model capability is the bottleneck. As of 2026-05-05, a realistic local stack might look like:

- **Drafting / summarization / extraction:** a 30B–70B class model running locally (Llama 3.x derivatives, Mistral Large, Qwen 2.5) at acceptable latency on consumer hardware (Mac Studio M2/M3 Ultra, dedicated workstation with 2x4090 or H100).
- **Long-context understanding:** harder. Local 128k+ context is achievable but expensive. May require chunking strategies the cloud model doesn't.
- **Reasoning-heavy tasks (planning, multi-step decomposition):** the gap between local and frontier is widest here. This is the work that genuinely benefits from cloud frontier models. For restricted content, the answer is "do the reasoning-heavy planning at the cloud tier on synthetic / redacted versions; do the actual content work at the local tier."

The pattern explicitly accepts a quality drop at the restricted tier in exchange for the privacy floor. The user is making a tradeoff, and the system should make that tradeoff legible — e.g., a banner in the agent's response: *"This response was generated by a local model because the source file is sensitivity:restricted. Reasoning quality may be lower than the cloud baseline."*

### 3. The enforcement layer is a hook, not a convention

A `PreToolUse` hook on whatever tool the agent uses to call models (in Claude Code, this means an MCP server or a direct API call from a Bash command — the hook surface depends on the harness). The hook:

1. Inspects the tool input for any file path or content that came from a restricted-tier source.
2. If found, denies the cloud model call. Either redirects to a local-model command or returns an error directing the agent to invoke the local-model path explicitly.

The convention layer (CLAUDE.md rule: "for restricted content, use the local model") is too weak. The agent's best intention will get overridden by a forgotten rule or a fresh-context session. The hook makes the policy mechanical.

## What's missing today (and what would close each gap)

### Missing: a routing layer

The cloud-model API call (Anthropic / OpenAI / Google) and the local-model API call (Ollama / llama.cpp / LM Studio) are different surfaces. The agent currently picks one statically per session.

What closes this: a thin router (HTTP proxy or MCP server) that exposes a unified API, reads a "sensitivity hint" from request metadata or context, and forwards to the appropriate backend. Several open-source projects are converging on this shape (LiteLLM, AI Gateway proxies, the LangChain/LlamaIndex provider abstraction layer). None yet has first-class "route by content sensitivity" as a configuration primitive — they all route by model preference or cost.

### Missing: a policy enforcement hook

Even if routing exists, nothing enforces *which* tier goes to *which* backend without an explicit hook. The hook needs to read the sensitivity context for the request and either confirm the routing matches the policy or block.

What closes this: a `PreToolUse` hook on the model-call tool. Implementation depends on the harness (Claude Code MCP, Continue.dev, Cursor) — but the shape is the same as the existing Read hook, just operating on a different tool.

### Missing: capable-enough local models for the target workflows

This is the biggest gap. Today's 30B–70B local models are good enough for:
- Summarizing a transcript
- Drafting a short message
- Extracting structured data from a document
- Q&A grounded in a single doc

They are not yet good enough for:
- Multi-document synthesis with subtle reasoning (e.g., the `/incorporate` skill's routing decisions)
- Voice-doc-quality drafting where the difference between "passable" and "good" is material
- Complex agentic workflows with tool use, planning, and adaptive replanning

What closes this: time. Local model quality has improved sharply year over year and the trend isn't obviously slowing. The pattern's job is to be ready when the local tier crosses the workflow threshold, not to wait until that happens before designing.

### Missing: workflow wiring

Even with routing and capable models, the existing skills (`/transcript-processor`, `/incorporate`, `/meeting-brief`) don't know to invoke the local path. They make model calls implicitly. Each skill needs either:
- A skill-level config that says "I touch sensitive content, prefer local," or
- The router making the decision transparently based on inputs the skill provides

Skill-level config is more honest (the skill author thought about it). Router-transparency is more reliable (no skill author can forget). Probably both: skills declare intent, router enforces.

### Missing: an audit trail

Today, the user can't easily verify *that* a particular session's restricted-content processing went local. The local model and the cloud model both produce text; there's no fingerprint.

What closes this:
- The router logs every request with model destination + content-sensitivity. The log is local-only.
- The agent's response includes a footer / banner naming which model produced it, especially when the local path was used.
- A periodic audit script (`scripts/sensitivity-audit.sh`) that grep'd recent session logs for cloud-model calls referencing restricted-tier files would surface policy violations after the fact.

## How to Adopt (when feasible)

1. **Establish the sensitivity tier system first.** This pattern is meaningless without [`sensitivity-tiered-access-control.md`](sensitivity-tiered-access-control.md). The tier vocabulary and the enforcement hooks are prerequisites.
2. **Identify the actual restricted workflows.** Don't speculate. Find the real files with `sensitivity: restricted` and the real skills that process them. The list will be short. That's good — small surface area is the whole reason the local tier is feasible.
3. **Pick the local model and prove it on a single workflow.** Start with one task that lives entirely in the restricted tier (e.g., "summarize a counseling transcript"). Run it locally with a 30B–70B model. If the output quality is acceptable, that's one workflow off the cloud. If not, defer this workflow and pick another.
4. **Stand up a routing layer.** Even a manual one. A bash script that takes `sensitivity` as an argument and calls the appropriate model. Get the policy mechanical before automating.
5. **Wire the routing into the harness.** A `PreToolUse` hook on the model-call tool that reads sensitivity context and enforces routing. This is the load-bearing piece.
6. **Write the workflow-by-workflow migration plan.** Some workflows will move local easily; others will sit on the cloud tier indefinitely. Document the decision per workflow.
7. **Re-audit at each major local-model release.** When a new model crosses the capability threshold for a previously-deferred workflow, migrate it.

## Watch-outs

**This is not "use a local model for everything."** That's a cost decision, not a privacy decision, and it has a different shape. This pattern routes *only* the restricted tier locally because the privacy cost of cloud processing for that tier is unacceptable. The other tiers still go cloud because the productivity gap is real.

**Capability-floor honesty.** When a workflow can't be done well locally, *don't fake it.* Either keep that workflow on the cloud tier (and re-tier the content if the user accepts the cloud-processing cost), or skip that workflow for restricted content. Faking it (running the cloud model on lightly-redacted content) creates the worst of both worlds: the user thinks the privacy floor held when it didn't.

**The local model is not a panacea against the agent.** A local-running malicious or buggy agent can still leak content via filesystem writes, network calls outside the model API, or copy-paste into other tools. The pattern protects against the dominant case (restricted content flows to cloud-model API) — not against general agent misbehavior.

**Plan for the bridge tier.** While local models lag for high-quality drafting on restricted content, there's a useful bridge tier: **local model with cloud-model planning on synthetic content.** Example: have the cloud model plan how to summarize a transcript (using only the structure, not the content), then have the local model execute the plan against the real content. The plan crosses the network boundary; the content doesn't. This is a workable interim posture before local models close the quality gap entirely.
